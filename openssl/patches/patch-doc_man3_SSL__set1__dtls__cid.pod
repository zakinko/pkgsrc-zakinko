+=head1 DESCRIPTION
+
+A Connection ID (CID) is an identifier carried in every protected DTLS record
+of a connection. A receiver that finds its connections by the CID rather than
+by the address and port of the sender keeps a connection when the peer's
+address changes, for example after a NAT rebinding. OpenSSL implements the
+"connection_id" extension and the record format of RFC 9146 for DTLS 1.2, and
+the use of Connection IDs in DTLS 1.3 described in RFC 9147, where the CID is
+carried in the unified header from the handshake epoch on.
+
+Each side of a connection chooses the CID it wants to find in the records it
+receives, and sends it to the peer in the extension; the peer puts it in every
+record it protects. The two directions are independent, and a side that asks
+for an empty CID receives records without one.
+
+SSL_set1_dtls_cid() enables the extension on the DTLS connection I<s> and sets
+I<cid>, of I<cid_len> bytes, as the CID the peer is asked to use when sending
+to it. I<cid_len> may be zero, with I<cid> NULL: the connection then sends with
+the peer's CID but receives records without one. I<cid_len> must not exceed
+B<SSL_DTLS_CID_MAX_LEN>. A client offers the extension in its ClientHello; a
+server answers a ClientHello that offers it. The CID takes effect with the
+keys of the next handshake and cannot be changed while a handshake is in
+progress. The CID is copied.
+
+SSL_clear_dtls_cid() disables the extension on I<s> from the next handshake
+on.
+
+SSL_get0_dtls_cid() reports whether the extension was negotiated in the last
+handshake on I<s>. If it was, I<*own> and I<*own_len> are set to the CID in
+the records I<s> receives, and I<*peer> and I<*peer_len> to the CID in the
+records it sends; a zero length means no CID in that direction, and the
+pointer may then be NULL. Otherwise all four are set to NULL and zero. Any of
+the output arguments may be NULL. The pointers remain valid until the next
+handshake or until I<s> is freed.
+
+SSL_set_dtls_rrc() turns the Return Routability Check of RFC 9853 on or off
+for the next handshake on I<s>. It is on by default and is offered, or
+accepted, only together with the Connection ID. SSL_get_dtls_rrc() reports
+whether it was negotiated in the last handshake.
+
+=head2 Changing the CIDs in DTLS 1.3
+
+After a DTLS 1.3 handshake that negotiated Connection IDs, either side can give
+the other further CIDs to use when sending to it (RFC 9147 section 9).
+
+SSL_dtls_new_connection_id() queues a NewConnectionId message with one new CID
+of the connection's own, of the length of the one it asked for in the
+handshake: the CID length is not carried in records, so all the CIDs a
+connection receives have the one length. With I<usage>
+B<SSL_DTLS_CID_IMMEDIATE> the peer must use it for all records from then on;
+with B<SSL_DTLS_CID_SPARE> it may. The old CIDs stay acceptable. A connection
+that receives with an empty CID cannot send this message.
+
+SSL_dtls_request_connection_id() queues a RequestConnectionId message asking
+the peer for I<num> spare CIDs. A connection that sends with an empty CID
+cannot send this message. OpenSSL answers a request with a NewConnectionId
+carrying up to the number asked for, and gives out at most 8 further CIDs over
+a connection; the RFC allows fewer, "including no CIDs at all". It keeps up to
+4 spare CIDs from the peer and discards the rest, as the RFC allows; spare CIDs
+are kept for use when moving to another path, which OpenSSL does not do on its
+own.
+
+Either message is sent the next time the connection is driven, for example by
+L<SSL_write(3)> or L<SSL_read(3)>, and a second of the same kind cannot be
+queued until the first has been acknowledged. Both fail on a connection that is
+not DTLS 1.3, has not finished its handshake, or did not negotiate a CID.
+
+=head2 Changes of peer address
+
+A connection created by a DTLS listener (see L<SSL_new_listener(3)>) that
+gives Connection IDs (B<SSL_VALUE_DTLS_LISTENER_CID_LEN>, see
+L<SSL_get_value_uint(3)>) has the CID the listener chose, which
+SSL_set1_dtls_cid() cannot replace, and is found by it when records arrive
+from an address other than its peer's. It then sends to the new address only when
+RFC 9146 section 6 allows: the record passed verification, it is newer than
+any record received before, and the new address has been found able to
+receive. The last is decided as follows.
+
+If the Return Routability Check was negotiated, the connection sends a
+path_challenge to the new address and moves there when the matching
+path_response comes back within one second (RFC 9853 section 5.1). Until then
+it keeps sending to the old address, so nothing larger than the challenge
+goes to an address that has not been validated. The enhanced check of RFC
+9853 section 5.2 is not implemented.
+
+Otherwise the callback set with SSL_CTX_set_dtls_peer_addr_change_cb() on the
+B<SSL_CTX> the connection was made from is asked, with the address the
+connection sends to now and the new one; it returns 1 to move and 0 to stay,
+and is asked again for later records from the new address. Without a
+callback the address does not change. A callback that returns 1 without
+having validated the new address in some way of its own (RFC 9853 section
+3.1) leaves the connection open to the attacks described in RFC 9146 section
+9.
+
+=head1 NOTES
+
+The record protection of RFC 9146 is implemented for AEAD ciphers (AES-GCM,
+AES-CCM, ChaCha20-Poly1305) and for CBC ciphers with Encrypt-then-MAC
+(RFC 7366). It is not implemented for CBC ciphers without Encrypt-then-MAC: a
+server does not accept the extension when such a cipher is negotiated, and a
+client aborts the handshake if a server accepts it with one.
+
+A record with a CID carries at most 2^14 - 1 bytes of data, one less than a
+record without one, because its plaintext also holds the content type and
+RFC 9146 limits that to 2^14 bytes.
+
+For a connection with a BIO of its own, rather than one created by a
+listener, OpenSSL does not change the address it sends to. Note however that
+a L<BIO_s_datagram(3)> whose socket is not connected sends to the source
+address of the last datagram it received, before OpenSSL has checked it, which
+RFC 9146 section 6 forbids; use a listener, or a connected socket.
+
+The CID is visible on the wire and identifies the connection for as long as
+it lasts. RFC 9146 section 8 discusses the privacy implications.
+
+=head1 RETURN VALUES
+
+SSL_set1_dtls_cid() returns 1 on success and 0 on error, which includes I<s>
+not being a DTLS connection.
+
+SSL_get0_dtls_cid() returns 1 if the extension was negotiated and 0
+otherwise.
+
+SSL_set_dtls_rrc() returns 1 on success and 0 if I<s> is not a DTLS
+connection.
+
+SSL_dtls_new_connection_id() and SSL_dtls_request_connection_id() return 1 if
+the message has been queued and 0 otherwise. SSL_get_dtls_rrc() returns 1 if the Return Routability Check was
+negotiated and 0 otherwise.
